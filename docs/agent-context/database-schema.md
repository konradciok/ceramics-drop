# Database Schema (Supabase)

> Moved verbatim from `AGENTS.md` (context-diet restructure). `AGENTS.md` keeps a short stub with the invariants; this file holds the full detail. Perishable feature state lives in `docs/STATUS.md`.

### Database Schema (Supabase)

- `piece_state`: `product_id` PK, `status` (available|reserved|sold), `reserved_until`, `order_id`, `showroom` (bool — visible but not purchasable, independent of `status`) + `showroom_entered_at` + `showroom_note`
- `drops`: `id`, `status` (active|ended), `ended_at` — ended via `/api/admin/end-drop`; ending a drop is pure bookkeeping and does NOT auto-move its pieces into the showroom (that's a separate, explicit `toggle-showroom` step)
- `product_interest`: anonymous showroom-interest capture (`product_id`, `email`, `message`, `consent_marketing`, `locale`), deduped per (`product_id`, `email`) via `POST /api/interest`; notifies the studio by email on genuinely new submissions only
- `orders`: UUID id, `payment_intent_id`, `status` (pending|paid|failed|expired|refunded), totals in minor units, contact JSON, `delivery_method`, `locale`, `currency` (pln|eur|gbp), `marketing` (jsonb — server-conversion context), `confirmation_email_sent_at`, `conversions_sent_at` (claim column — server-side purchase conversions are sent at most once per order), `private_sale_id` (nullable FK), `user_id` (nullable FK → `auth.users`, `ON DELETE SET NULL` — customer-account link, set at checkout or by verified-email backfill-on-login) + `user_unlinked_at` (deletion stamp; permanently excludes rows from backfill), `resend_email_id` (links the order to its Resend confirmation email so the Resend webhook can Sentry-alert on a bounce/complaint), `promo_code` (nullable, denormalized) + `discount` (minor units, default 0 — `subtotal` stays pre-discount; `total = subtotal − discount + shipping`); shipping (`20261124120000`, written from the Sendcloud release on): `delivery_country` (ISO alpha-2), `shipping_channel` (`inpost_shipx` | `sendcloud`; NULL = no carrier shipment, and a NULL on an order with an `inpost_shipment_id` reads as `inpost_shipx`), `delivery_point` (jsonb, the chosen pickup point), `tracking_url` (https only), `shipment_attempt` (int, default 0 — suffix of the Sendcloud `external_reference_id`, advanced only by an admin recreate)
- `order_items`: `order_id`, `product_id`, `unit_price` (minor units, in the order's currency), `variant` (jsonb — gift-card tier, or the snapshotted size/frame of a historical fine-art print line, rendered via `src/lib/legacy-print-lines.ts`)
- `private_sales`: `id`, `token`, `product_ids`, `expires_at`, `consumed_at` — single-use re-sale links for sold pieces (one paid order per token, enforced by a partial unique index)
- `webhook_events`: idempotency ledger for inbound webhooks — dedup on (`provider`, `provider_event_id`) with a leased `status`; used by the Stripe webhook (migrations `20260626120003` + `20260728120000`; it also holds historical Prodigi callback rows)
- `promo_codes` + `promo_redemptions`: promo-code definitions (percent or per-currency fixed amount, `applies_to` track, schedule window, `max_redemptions`, `newsletter_welcome` — at most one active) and their redemption ledger (`pending`→`redeemed`/`released`), claimed/settled by the `claim_promo_redemption()` / `settle_promo_redemption()` RPCs (migration `20260830120000_promo_codes.sql`). See `docs/promo-codes.md`.
- **Catalogue shadow tables** `products` (`type` ceramic-only since the print drop), `product_variants`, `product_media`, `product_drafts` + `catalog_audit_log`, plus `cms_documents`/`cms_document_versions` and the CMS-published `shipping_rates` — see [product-registry.md](product-registry.md) and [admin-cms-api.md](admin-cms-api.md)
- **Dropped 2026-11-22 (print shop moved to anna-ciok.com):** `fulfilment_jobs`, `prodigi_orders`, `pod_variants`, `print_fulfilment_assets`, `print_variant_asset_assignments`, `print_asset_uploads`, `print_asset_jobs`, `print_pricing_config`, `pricing_config_drafts`, `collections`, `collection_drafts`, their RPCs/triggers, and the print `products` rows (backed up before the drop). Kept as history: `orders.fulfilment_type = 'prodigi'`, `order_items.variant`, promo `applies_to = 'prints'`
- `reserve_pieces()` RPC: atomically reserves rows; returns array of conflicting product IDs (empty = success). `reserve_private_sale_pieces()` does the same for sold pieces behind a valid token. Both are re-entrant per order id (checkout calls them again after its orders insert to confirm the hold)
- `release_orphaned_checkout_hold(order_id, target)` RPC: checkout's guarded release — locks the order's reserved rows, answers `live_order` and frees nothing while a `pending`/`paid` order exists, else frees them to `available` (or `sold` for a private sale) and answers `released` (migration `20261125120000_release_orphaned_checkout_hold.sql`)

RLS is enabled; all server-side code uses the service-role key (`getSupabaseAdmin()`). That client's custom fetch (`src/lib/supabase-stall-retry.ts`) retries a bounded read (GET/HEAD carrying a caller `.abortSignal(...)`) once when no response headers arrive within 2.5 s — production timeouts were connections that stalled before reaching Supabase. Writes/RPCs and unbounded reads are never retried.
