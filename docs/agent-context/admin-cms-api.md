# Admin (Studio dashboard) + CMS API entrypoint

> Moved verbatim from `AGENTS.md` (context-diet restructure). `AGENTS.md` keeps a short stub with the invariants; this file holds the full detail. Perishable feature state lives in `docs/STATUS.md`.

### Admin (Studio dashboard)

A back-office UI lives **outside** the `[locale]` tree at `src/app/admin/` with its own `<html>`/`<body>` (overview KPIs, `orders`, `fulfillment`, `customers`, `inventory`, `products`, `content` — the last two drive the CMS publish path described under Product Registry; `promotions` manages promo codes with live redemption/revenue stats, on the same server-page → client-editor → `/api/admin/*` pattern as `pricing` — see `docs/promo-codes.md`). Server helpers are in `src/lib/admin/` (`data.ts` reads — `listOrders`/`getOrder`/`listInventory` take an optional injected Supabase client, defaulting to `adminSupabase()`; `clients.ts` client factories — `adminSupabase()`/`adminStripe()` build from `getCloudflareContext()`, plus pure `adminSupabaseFromEnv()`/`adminStripeFromEnv()` for callers outside a Workers request; `actions.ts` the four dependency-injected mutations; `fulfillment.ts` queue stages; `money.ts`, `route-helpers.ts`). Mutating actions are exposed under **`/api/admin/*`**: `refund`, `create-shipment`, `label`, `release-reservation`, `resend-confirmation` — each route is a thin adapter over the matching `src/lib/admin/actions.ts` function. `set-piece-status` (mark a piece sold/available from the inventory screen, `InventoryManager.tsx`), `toggle-showroom` (move pieces into/out of showroom), and `end-drop` (bookkeeping-only: `drops.status → ended`) all talk to Supabase directly rather than through `src/lib/admin/actions.ts` and have no Orders CLI equivalent.

In production every `/admin` and `/api/admin` request is gated by a **Cloudflare Access JWT**, verified in `worker.ts` via `src/lib/admin/access.ts` (path regex `^/admin(/|$)|^/api/admin(/|$)`, checked against `CF_ACCESS_TEAM_DOMAIN` / `CF_ACCESS_AUD` and the `ADMIN_ALLOWED_EMAILS` allowlist). Locally the gate is bypassed via `STUDIO_ADMIN_LOCAL_BYPASS`, and `local-admin/` is an nginx reverse proxy (`compose.yaml` → `host.docker.internal:3010`) so the dashboard is reachable over LAN during `npm run admin:dev:lan`.

**Orders CLI:** `npm run orders -- …` (`scripts/orders-cli.ts`) — reads order/inventory/fulfilment state and runs four of the five `/api/admin/*` mutations — refund, release-reservation, resend-confirmation, create-shipment; `label` is API-only (calling the same `src/lib/admin/actions.ts` functions with its own loaded Supabase/Stripe/InPost clients, built from `.env.local` → `.dev.vars` → `--env-file` → `process.env`, same precedence as `prodigi-cli`). Prefer this over raw SQL or the gated `/admin` UI for routine order debugging. Every mutation requires `--confirm <order-id>` and is blocked against a non-production Supabase project unless `--allow-nonprod` is passed. It also carries two non-mutating resources worth remembering: `webhook-config-check` (the Stripe subscription/API-version drift guard, see [webhook-fulfilment.md](webhook-fulfilment.md)) and `reconcile-refunds` (the offline full-refund convergence sweep — dry-run by default; `--confirm <uuid>` converges a single order, `--skip-relist` records a deliberate operator decision that a piece must NOT return to sale). Full usage in `docs/orders-cli.md`.

### CMS API (`CmsApi` entrypoint)

A private admin API for the separate `cms-ceramics` app, reachable **only** via a Cloudflare Service Binding named entrypoint (`CmsApi`, a `WorkerEntrypoint` subclass exported from `worker.ts` alongside the OpenNext default export and the DO re-exports) — never through Next.js routing or any public URL. Implementation lives entirely under `src/server/cms-api/`: `access.ts` independently re-verifies the Cloudflare Access JWT the CMS forwards (`Cf-Access-Jwt-Assertion`), checking the **CMS app's own** Access audience/team/owners (`CMS_ACCESS_TEAM_DOMAIN`/`CMS_ACCESS_AUD`/`CMS_OWNERS`) — a separate trust boundary from the storefront's own `/admin` gate (`src/lib/admin/access.ts`); `router.ts` + `request-handler.ts` dispatch `/v1/*` paths to handlers under `handlers/`; `mapping.ts` builds the canonical `Product` response from the catalog shadow tables plus the new `product_drafts`/`piece_state`/print-asset tables; `readiness.ts` computes print publish-blockers from the real `print_variant_asset_assignments`/`print_fulfilment_assets` state — the same predicate a publish attempt itself enforces. Every write carries `expectedRevision` (optimistic concurrency against `product_drafts`) and idempotent operations require an `Idempotency-Key` (leased-CAS ledger in `idempotency.ts`, its own `cms_api_idempotency_keys` table — shaped like but separate from the Stripe/Prodigi `webhook_events` ledger). The canonical contract is `contracts/cms-v1.json` (OpenAPI 3.1, `1.0.0`) with fixtures in `contracts/fixtures/`; data-model semantics (revision/publishedRevision/audit) are in `docs/cms-api-data-model.md`. S2/S3/S4-scoped operations (content, pricing, shipping-rates, assets, uploads, jobs) are documented in the contract but return `404 NOT_IMPLEMENTED` until their packages land — this is the router's default fallback, not a per-route stub. Provisioning a real isolated integration environment for the CMS to test against is a human runbook, `docs/cms-api-integration-environment.md`, not something either repo's CI does automatically.
