### Webhook Fulfillment

`src/lib/webhook.ts` → `handleStripeEvent()` handles Stripe webhooks at `/api/stripe/webhook` (snapshot / full-payload event destination). The route wraps every delivery in the **shared `webhook_events` idempotency ledger** (also used by the Prodigi callbacks): a leased CAS claims the event, and any handler throw releases the lease so Stripe's retry reclaims it immediately instead of being deduped-and-dropped inside the lease window. A **200 dedupe** is reserved for a ledger row that reached `done` — any competing delivery (active lease, lost claim CAS, 23505 insert race over a non-done row) answers **409** so Stripe redelivers after the lease (Plan 06; expect concurrent duplicate deliveries to show as failed-then-succeeded in Stripe — do not tune the 409s away).

**API-version ritual:** stripe-node ≥ v12 always pins its **bundled** API version on every request — the account-default version is never used (https://docs.stripe.com/sdks/set-version). `src/lib/stripe.ts` additionally passes that version explicitly (`STRIPE_API_VERSION`, currently `2026-05-27.dahlia` from `stripe@22.2.1`); the `apiVersion` option is typed as the bundled-version literal, so an `npm update stripe` that moves the bundled version fails `npm run typecheck` instead of silently changing payload shapes. The ritual on every `stripe` package bump: update `STRIPE_API_VERSION` in `src/lib/stripe.ts`, update the snapshot webhook endpoint's API version (Stripe Dashboard) in lockstep so incoming event payloads stay aligned with the SDK types, then verify with `npm run orders -- webhook-config-check`. (Confirm the exact bundled version from the installed `stripe` package / `package-lock.json` after a bump — it is not inferable from the `^` range in `package.json`.)

Event handling (the full set is `HANDLED_STRIPE_EVENTS` in `src/lib/webhook.ts`; the live endpoint's subscriptions are drift-gated by `npm run orders -- webhook-config-check`):
- `payment_intent.succeeded` → `markPaid` (idempotent; also sends the customer order-confirmation email + studio new-order email, guarded by `confirmation_email_sent_at`), then `trackPurchase` (server-side Meta CAPI + GA4 MP, consent-gated, skipped unless `order.status = paid`, claimed once per order via `orders.conversions_sent_at` so a redelivery can't double-send; the claim is synchronous but the outbound send is deferred to `ctx.waitUntil` so it never holds the webhook response, and both calls are bounded by an 8s `AbortSignal.timeout`), then `ensureInvoiced` (errors swallowed — Stripe gets 200, no retry), then fulfilment: **ceramic orders** call `createShipment` (InPost; re-throws retryable errors so Stripe retries up to 3 days), **print orders** call `enqueueProdigi()` (`src/server/fulfilment/enqueue.ts`) to push a job onto the Cloudflare Queue for async Prodigi submission
- `payment_intent.payment_failed` / `payment_intent.canceled` → `releaseHold` (frees reserved pieces)
- `charge.refunded` (full refund only) → `releaseSale` (relists pieces; on a real `paid`→`refunded` transition it also fires a GA4-only `refund` event via `sendRefundConversion` to reverse the recorded revenue — Meta has no un-fire, so CAPI is not involved)
- `charge.dispute.closed` (lost only) → `releaseSale`
- `charge.dispute.created` → alert-only (Sentry + a due-date-bearing studio email — the evidence clock starts at creation and a missed deadline is an automatic loss); the send is allowed to throw so Stripe redelivers a failed alert; no order state changes until the dispute closes
- `refund.failed` → alert-only (Sentry + studio email); the order stays `refunded` in the DB — a refund the customer never received (closed account / expired card, up to ~30 days later) has no automatic remedy and a human must re-issue it by another way

`worker.ts` wraps the OpenNext handler with two extra handlers: a **cron** (every 15 min) that runs five sweeps — (1) expire abandoned orders older than 1 hour (claims a recoverable `expiry_claim_at` lease BEFORE the irreversible PaymentIntent cancel, then frees reserved pieces — pieces first, lease-fenced `pending→expired` CAS last; a paid-on-pending `refund_pending_at` marker stranded >24 h fires the M-15 alert), (2) alert on `failed_action_required` fulfilment jobs, (3) the M-10 watchdog for jobs stranded >2 h in a pre-submission state (queued / submitting / retryable), (4) the M-12 reconciliation sweep that re-polls stale post-submission Prodigi orders and re-runs the callback merge, and (5) the promo-redemption reconciliation sweep (`src/lib/promo-reconcile.ts`) that converges pending `promo_redemptions` left stale >2 h and alerts if a paid order still has one (`markPaid` should have settled it) — every sweep self-alerts to Sentry (plus logs) if it throws, since a dead `scheduled` handler would otherwise show green in Cron Past Events; and a **queue consumer** that drains the `prodigi-fulfilment` queue (`src/server/fulfilment/process-job.ts`; transient errors retry with exponential backoff capped at 1 h) and an **alert-only `prodigi-fulfilment-dlq` consumer** (per batch: log + Sentry + one studio email, then ack every message — it never retries, so a poison message cannot loop back through the system).
